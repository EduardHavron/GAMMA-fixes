# FX-TGEN: генерация заданий без повторных сканов мира + профилировщик заданий
Статус: черновик        Проверка в игре: не проводилась        Мод: `zz Task Generation Speed Fix`        Скрипты: `gamedata/scripts/zz_xrrfix_tgen*.script` (ускорение: `zz_xrrfix_tgen.script` — точка входа и схема вызовов, по файлу на часть и общий код), `gamedata/scripts/zz_xrrfix_tgen_prof.script` (профилировщик)
Где ставить: хост (там генерируются задания; в соло тоже работает; у пира ставится вместе с пакетом и ничего не меняет)        Зависит от: Anomaly `axr_task_manager`, `xr_conditions.has_completed_task_prerequisites`; для bounty — PDA Taskboard Redesign v1.3 (`z_taskboard_bounty_variants`); без него bounty-часть пропускается        Лог-маркеры: `[XRRFIX] tgen: prerequisites memo installed (5000 ms)`, `[XRRFIX] tgen: bounty scan shared (snapshot 5000 ms)`, `[XRRFIX] tgen: measure scan shared (snapshot 5000 ms)`, `[XRRFIX] tgen: delivery scan shared (snapshot 5000 ms)`, `[XRRFIX] taskprof: installed (<N> functions timed)`

## Проблема
После FX-QLIST «Обновить» в Taskboard у пира больше не останавливает картинку хоста на секунды, но хост лагает примерно
так же, только дольше: суммарная работа генерации заданий не уменьшилась, она растянута на кадры, а один запрос может
стоить больше бюджета кадра (FX-QLIST, «Ограничения»).

## Причина
На каждый запрос пира хост генерирует задания NPC (`xrr_patch_quests.OnQuestListRequest`, `xrr_patch_quests.script:1664`):
`axr_task_manager.generate_available_tasks`, затем для каждого найденного задания `capture_offer_message` → его
`on_job_descr`. Дорогими по коду выглядят две вещи; какая из них главная на самом деле — покажет профилировщик
`[НЕ ПРОВЕРЕНО]` (замеров по функциям ещё нет).

1. **Предусловия заданий считаются заново для каждого NPC.** `generate_available_tasks` (Anomaly `axr_task_manager.script`)
   для каждой секции задания с префиксом NPC зовёт `xr_conditions.has_completed_task_prerequisites(nil, nil, {task_id})`.
   Предусловие `validate_assault_task` (Tasks QoL Pack, `tasks_assault.script`; 199 заданий из конфигов GAMMA) без готовой
   цели обходит все смарты зоны (`SIMBOARD.smarts_by_names`) и их отряды; при неудаче ничего не кэширует — следующий NPC
   сканирует снова. У сим-NPC префикс общий (`simulation_task_`), так что 40–70 NPC в пачке проверяют одни и те же задания.
   Вызов идёт с `actor = nil`, `npc = nil`, но это не значит, что результат не зависит от NPC: часть предусловий берёт
   NPC диалога сама — `validate_measure_task` (Oleh's Tasks Crash Fixes, `tasks_measure.script`) зовёт
   `mob_trade.GetTalkingNpc()` и кэширует цель замера в `cache[task_id][task_giver_id]`, а `setup_measure_task` при выдаче
   читает именно эту запись («can't get cached result», если её нет). На хосте в коопе NPC запроса подставляет xrRazom
   (`set_peer_dialog_npc`), в соло — диалог.
2. **Bounty: полный перебор 65 534 серверных объектов на каждое задание.** Действующий `xr_effects.setup_bounty_task` —
   замена из PDA Taskboard Redesign v1.3 (`z_taskboard_bounty_variants.script`, ставится на `on_game_load`; мод выше
   Tasks QoL в порядке MO2). Его локальная `build_variants(task_id, p)` делает `for id = 1, 65534 do sim:object(id)` и
   отбирает живых сим-сталкеров в отрядах нужных фракций. Вызывается из `variant_list`, когда у задания нет живых
   кэшированных вариантов — на холодном «Обновить» это каждое bounty-задание каждого NPC, по полному скану на задание.
3. **Замер и доставка: свой полный перебор на каждого NPC.** `validate_measure_task` (Oleh's Tasks Crash Fixes,
   `tasks_measure.script`; поверх — обёртка G_FLAT's More Measurement Task Maps, держит оригинал в локальной
   `validate_measure_task_original` и ставит режим поиска 5) и `xr_effects.on_init_delivery_task` (Tasks QoL,
   `tasks_delivery.script`; на хосте поверх — защита xrRazom `xrr_patch_task_guards`, оригинал в её upvalue `orig`)
   зависят от NPC диалога и кэшируют результат на NPC, поэтому память предусловий (п. 1) их не делит, а каждый вызов
   перебирает `1..65534`. Замер у хоста (2026-10-27, `xray_drago.log`): пачка 40 NPC — `validate_measure_task`
   72 вызова, 3654 мс из 3691 мс генерации; доставка без цели (`simulation_task_48 ... no target found`) ничего не
   кэширует и перебирает мир на каждом «Обновить» (14 вызовов, 904 мс за 4,7 с).

## Решение
`zz_xrrfix_tgen.script` (точка входа), в `on_game_start` под `pcall`, каждая часть один раз. Файлы: `_memo`, `_bounty`,
`_measure`, `_delivery` — части; `_snapshot` — общий снимок мира; `_hooks` — поиск и подмена чужих функций;
`_measure_copy`, `_delivery_copy` — дословные копии заменённых функций. Схема, кто кого вызывает, — в шапке
`zz_xrrfix_tgen.script`.
- **Память предусловий.** `xr_conditions.has_completed_task_prerequisites` заменяется обёрткой. Вызов с `actor == nil`,
  `npc == nil` и строковым `p[1]` (так зовёт генерация) отвечает из памяти, если тот же `task_id` считался меньше 5000 мс
  назад (`time_global`); иначе зовёт оригинал и запоминает результат. Остальные вызовы (с актором или NPC — условия
  логики) идут в оригинал без памяти. `on_level_changing` очищает память.
  Пока считается оригинал, `mob_trade.GetTalkingNpc` временно обёрнут счётчиком: если предусловие задания обратилось к NPC
  диалога, задание помечается «зависит от NPC» и дальше всегда считается оригиналом, без памяти (у таких модов свой кэш
  на NPC).
- **Общий снимок для bounty.** Принудительно загружает `z_taskboard_bounty_variants`, через `debug.getupvalue` находит
  `variant_list` (upvalue `GetVariantInfo`) и в нём `build_variants`, а у неё — помощники мода (`candidate_relation`,
  `is_smart_valid`, `level_of`, `selected_blacklist`, `faction_lookup_from_params`, `candidate_valid`, `shuffled_copy`,
  `blacklisted_maps`, `MAX_VARIANTS`). Если чего-то нет — `[XRRFIX] tgen: Taskboard bounty selector not found, bounty part
  skipped`. Иначе `debug.setupvalue` ставит в `variant_list` свою `build_variants`:
  - снимок: один перебор `1..65534` с тем же отбором, что у оригинала, но без фильтра фракций (`candidate_relation` с
    таблицей «любая фракция»), плюс `is_smart_valid`, карта (`level_of`) не из `blacklisted_maps`; для каждого кандидата
    запоминаются фракция, отношение, карта и «на соседнем уровне» (`simulation_objects.is_on_the_nearby_level`). Снимок
    живёт 5000 мс, `on_level_changing` его сбрасывает;
  - задание: из снимка берутся кандидаты фракций задания (`faction_lookup_from_params(p)`), без карт из
    `selected_blacklist()`, и раскладываются, как у оригинала: при `p[3] == "true"` не соседние — в «прочие»;
    порядок выбора тот же (враги, нейтралы, прочие враги, прочие нейтралы, каждая группа перемешана), до `MAX_VARIANTS`;
  - каждый выбранный кандидат перед добавлением проверяется `candidate_valid(id, p)` мода — умерший или сменивший
    фракцию за время жизни снимка пропускается.
- **Один перебор мира на всех.** Снимок общий: части регистрируют сборщики, каждый за один проход `1..65534` собирает
  свой список (bounty — как выше; замер — аномалии всех типов `anomaly_types`: id, секция, уровень, `online`; доставка —
  командиры сим-отрядов, отбор как у оригинала: живой сталкер `sim_default` без story id, командир отряда `sim_squad`
  с `current_action == 1`; запоминаются фракция, уровень, «тот же уровень» и «связанный уровень»). Снимок живёт
  5000 мс, `on_level_changing` его сбрасывает.
- **Замер.** В цепочке обёрток `xr_conditions.validate_measure_task` ищется функция с upvalue `cache` и `anomaly_types`
  (оригинал); на её место (в upvalue обёртки G_FLAT или в таблицу, если обёртки нет) ставится копия оригинала, в которой
  перебор мира заменён списком аномалий снимка. Остальное как у оригинала: NPC диалога, его `cache[task_id][giver_id]`,
  фильтр по типам, `blacklisted_maps` (upvalue или переменная модуля `tasks_measure`, её меняет G_FLAT), северные карты
  `blacklist_helper`, динамические аномалии, режим поиска, случайный выбор. Без оригинала —
  `[XRRFIX] tgen: validate_measure_task not recognised, measure part skipped`.
- **Доставка.** Так же для `xr_effects.on_init_delivery_task` (upvalue `delivery_cache` и `faction_list`; место — в
  upvalue `orig` защиты xrRazom или в таблице): копия оригинала, поиск командиров заменён списком снимка, фильтр
  фракций по NPC диалога, «нет цели» — как у оригинала (`TaskBlacklist`, без кэша), но без нового перебора. Без
  оригинала — `[XRRFIX] tgen: on_init_delivery_task not recognised, delivery part skipped`.
- Счётчики для профилировщика: попадания и промахи памяти, сколько снимков построено и сколько раз переиспользован.

`zz_xrrfix_tgen_prof.script` (диагностика), в `on_game_start` регистрирует `actor_on_first_update`, где один раз (после всех
патчей `on_game_start` и `on_game_load`) оборачивает таймером:
`axr_task_manager.generate_available_tasks`, `generate_ongoing_tasks`, `trigger_fetch_func`,
`xr_conditions.has_completed_task_prerequisites` и функции заданий из списка в скрипте (предусловия и `on_job_descr`
из конфигов GAMMA: `validate_assault_task`, `setup_bounty_task`, `drx_sl_create_quest_stash` и др.; общие условия логики
вроде `squad_exist` не оборачиваются). Время — `profile_timer` (мкс), без него `os.clock`; время вложенных вызовов входит
во внешние. В `actor_on_update`: если с последнего замера прошло ≥ 1000 мс и набрано ≥ 5 мс, пишет итог и обнуляет:
```
[XRRFIX] taskprof: <S> s, generate <N> calls <X> ms | memo <h>/<h+m> hits, world snapshots <b> built, <r> reused
[XRRFIX] taskprof: #<i> <имя> | total <X> ms | calls <N> | max <Y> ms        (до 8 строк, по убыванию total)
```

## Требования

### FX-TGEN-001 Установка памяти предусловий  [auto]
Фикс ДОЛЖЕН один раз заменить `xr_conditions.has_completed_task_prerequisites` и записать лог-маркер. Без функции —
`[XRRFIX] tgen: has_completed_task_prerequisites missing, memo skipped`. Повторный `on_game_start` НЕ ДОЛЖЕН оборачивать
ещё раз.

### FX-TGEN-002 Память предусловий  [auto]
Вызов `(nil, nil, {task_id})` ДОЛЖЕН возвращать результат оригинала, а повторный вызов того же `task_id` раньше 5000 мс —
тот же результат без вызова оригинала.
- Дано оригинал вернул `false` для `t1` в t=0. Когда `t1` спрошен в 4999 мс. Тогда `false`, оригинал вызван 1 раз.
- Когда `t1` спрошен в 5000 мс. Тогда оригинал вызван снова.
- Разные `task_id` запоминаются отдельно.

### FX-TGEN-003 Вызовы логики без памяти  [auto]
Вызов с актором или NPC (не `nil`) или без строкового `p[1]` ДОЛЖЕН каждый раз уходить в оригинал с теми же аргументами
и ничего не запоминать.

### FX-TGEN-004 Сброс при смене уровня  [auto]
`on_level_changing` ДОЛЖЕН очищать память предусловий и снимок мира.

### FX-TGEN-005 Установка bounty-части  [auto]
Фикс ДОЛЖЕН найти `build_variants` в `variant_list` модуля `z_taskboard_bounty_variants`, заменить её один раз и записать
лог-маркер. Без модуля, без `debug.getupvalue`/`debug.setupvalue` или без любого из помощников — строка
`[XRRFIX] tgen: Taskboard bounty selector not found, bounty part skipped`, оригинал не меняется.

### FX-TGEN-006 Один скан на снимок  [auto]
Несколько вызовов `build_variants` в пределах 5000 мс ДОЛЖНЫ делать не больше одного перебора серверных объектов;
после 5000 мс — новый перебор.
- Дано три bounty-задания разных фракций подряд. Тогда `alife():object` вызван не больше 65 534 раз.
- `take_stats` (счётчики для профилировщика) НЕ ДОЛЖНА падать, если модуль части не загрузился: его счётчики — нули.

### FX-TGEN-007 Отбор как у оригинала  [auto]
Для каждого задания результат ДОЛЖЕН содержать только кандидатов, которых отобрал бы оригинал для тех же `p`: фракция из
`faction_lookup_from_params(p)`, живой сим-сталкер в отряде (отбор `candidate_relation`), `is_smart_valid`, карта не
из `blacklisted_maps` и не из `selected_blacklist()`; при `p[3] == "true"` — сначала кандидаты на соседних уровнях;
порядок групп: враги, нейтралы, затем прочие враги, прочие нейтралы; не больше `MAX_VARIANTS`.
- Дано кандидаты: враг-бандит рядом, нейтрал-сталкер рядом, враг-бандит далеко, задание на бандитов с `p[3]="true"`.
  Тогда в результате только бандиты, ближний первым.
- Помощники и `blacklisted_maps` берутся из upvalue `variant_list`, затем `build_variants`, затем `append_unique`;
  при совпадении имён побеждает первое найденное. Дано у `append_unique` свой local `blacklisted_maps` с картой
  кандидата. Тогда кандидат выбран, как у оригинала.

### FX-TGEN-008 Проверка перед выдачей  [auto]
Каждый кандидат из снимка ДОЛЖЕН проходить `candidate_valid(id, p)` модуля перед добавлением; не прошедший пропускается,
вместо него берётся следующий.

### FX-TGEN-009 Профилировщик: установка  [auto]
Профилировщик ДОЛЖЕН оборачивать функции в `actor_on_first_update` один раз (повторный вызов не оборачивает) и записать
лог-маркер с числом обёрнутых функций. Отсутствующие функции пропускаются молча. Обёртка ДОЛЖНА возвращать результаты
оригинала, а ошибку оригинала — пробрасывать после замера.

### FX-TGEN-010 Профилировщик: итог  [auto]
Итог ДОЛЖЕН выводиться в первом `actor_on_update`, когда с последнего замера прошло ≥ 1000 мс и набрано ≥ 5 мс: строка
сводки и до 8 строк функций по убыванию суммарного времени (формат — в «Решении»); затем счётчики обнуляются. Меньше 5 мс —
ничего не пишет и обнуляет. Числа подставляются через `string.format` (Anomaly `printf` подставляет только `%s`).

### FX-TGEN-012 Предусловия, зависящие от NPC  [auto]
Если при подсчёте предусловия задания был вызван `mob_trade.GetTalkingNpc`, результат НЕ ДОЛЖЕН браться из памяти ни
сейчас, ни при следующих вызовах этого `task_id` (до `on_level_changing`); `mob_trade.GetTalkingNpc` после вызова ДОЛЖЕН
быть восстановлен, в том числе при ошибке оригинала.
- Дано предусловие `m1` зовёт `GetTalkingNpc` и отвечает `true` для NPC 1 и `false` для NPC 2. Когда `m1` спрошен для NPC 1,
  затем для NPC 2 через 100 мс. Тогда ответы `true`, `false`, оригинал вызван 2 раза.
- Без `mob_trade` память работает как в FX-TGEN-002.

### FX-TGEN-013 Замер: установка  [auto]
Фикс ДОЛЖЕН найти оригинал `validate_measure_task` (upvalue `cache` и `anomaly_types`) в таблице или в цепочке обёрток,
поставить копию на его место один раз и записать лог-маркер; обёртки сверху (G_FLAT) ДОЛЖНЫ остаться и работать.
Без оригинала или без `debug` — строка `... measure part skipped`, ничего не меняется.

### FX-TGEN-014 Замер: результат как у оригинала  [auto]
Для любого NPC копия ДОЛЖНА давать тот же ответ и ту же запись `cache[task_id][giver_id]`, что оригинал на том же мире и
тех же случайных числах, и делать не больше одного перебора на снимок для всех NPC.
- Дано три NPC, один квест на замер. Тогда записи кэша как у оригинала, `alife():object` вызван 65 534 раза (у оригинала —
  втрое больше).
- Дано `blacklisted_maps` модуля изменён во время игры. Тогда копия видит изменение.

### FX-TGEN-015 Доставка: установка  [auto]
Фикс ДОЛЖЕН найти оригинал `on_init_delivery_task` (upvalue `delivery_cache` и `faction_list`) в таблице или под защитой
xrRazom, поставить копию на его место один раз и записать лог-маркер; защита xrRazom (на пире — ничего) ДОЛЖНА остаться.

### FX-TGEN-016 Доставка: результат как у оригинала  [auto]
Для любого NPC копия ДОЛЖНА выбирать ту же цель и класть то же в `delivery_cache` и `save_var`, что оригинал, а при
отсутствии цели — ставить `TaskBlacklist[task_id] = true` без нового перебора в пределах снимка.
- Дано два NPC, ближняя и дальняя доставка. Тогда цели как у оригинала, один перебор (у оригинала — по одному на вызов).
- Дано командир отряда с `current_action ~= 1` с наибольшим id. Тогда он не цель, как у оригинала.

### FX-TGEN-011 В игре  [manual]
- Дано кооп, пир у базы «Свободы». Когда пир жмёт «Обновить» в Taskboard (первый раз после загрузки). Тогда просадка у
  хоста короче и слабее, чем без фикса; в логе хоста `taskprof`-итог с `memo` попаданиями и `bounty snapshots`, суммарное
  время `generate` меньше, чем в итоге без `zz_xrrfix_tgen.script`.

## Безопасность
- Выбор заданий тот же: из памяти отвечают только предусловия, не обращавшиеся к NPC диалога (FX-TGEN-012), в пределах 5 с
  мир меняется мало; bounty-кандидаты
  отбираются теми же функциями мода и перепроверяются его же `candidate_valid` перед выдачей.
- Соло: то же ускорение (диалог с несколькими NPC подряд за 5 с). Пир: генерацию делает хост; на пире память и снимок
  могут не использоваться — без вреда.
- Без PDA Taskboard Redesign bounty-часть не ставится; память предусловий работает отдельно.
- Профилировщик меряет только перечисленные функции заданий; вне генерации их почти не зовут. Лог — одна сводка на пачку.

## Вне области / известные ограничения
- Задание, ставшее доступным или недоступным за последние 5 с (например, отряд пришёл на смарт), может показаться в старом
  состоянии до 5 с. Цель assault-задания при выдаче всё равно проверяет `setup_assault_task` Tasks QoL.
- Порядок кандидатов внутри снимка отличается от перебора по id; выбор и так случайный (`shuffled_copy`).
- Bounty-часть опирается на внутреннее устройство `z_taskboard_bounty_variants` PDA Taskboard Redesign v1.3 (имена
  локальных функций). После обновления мода — сверить; при несовпадении фикс сам пропустит эту часть (FX-TGEN-005).
- Остальные `on_job_descr` (тайники `drx_sl_create_quest_stash`, NTA и др.) не ускоряются; если профилировщик покажет их
  дорогими — это следующий шаг.
- Замер у KDVFirehawk (хост, 2026-10-26, первое «Обновить»): `generate 30 calls 148 ms`, память 1890/2051;
  `validate_measure_task` 3 вызова ≈ 97 мс, `on_init_delivery_task` 2 вызова ≈ 95 мс, `setup_bounty_task` (снимок) ≈ 50 мс —
  все три делают свой полный перебор 65 534 объектов. Просадка 90 → 60 FPS на ~0,5 с вместо 3–5 с остановки.
  Сделано (FX-TGEN-013…016): замер и доставка берут цели из общего снимка.
- Замер и доставка — **копии** чужих функций (Oleh's Tasks Crash Fixes `tasks_measure.validate_measure_task`, Tasks QoL
  `tasks_delivery.on_init_delivery_task`). После обновления этих модов — сверить копии с оригиналами; если пропадут
  нужные локальные переменные, фикс сам пропустит часть (лог `... not recognised`), но изменения логики внутри функции
  сам не заметит.
  Как сверять: копии лежат в `zz_xrrfix_tgen_measure_copy.script` и `zz_xrrfix_tgen_delivery_copy.script` (фабрики
  `make_validate_measure_task` и `make_on_init_delivery_task`) дословно, включая форматирование; каждое отличие помечено
  `-- XRRFIX:`. Тело фабрики без одного таба отступа сравнивается обычным диффом с функцией оригинала — разница должна
  быть только в помеченных местах.
- Профилировщик — диагностика; после замеров его можно убрать из мода.
