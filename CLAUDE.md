# CLAUDE.md — как мы разрабатываем этот репозиторий

Правила для людей и для Claude Code. Обзор для игроков — `README.md`, правила спецификаций и реестр ID — `specs/README.md`,
запуск тестов — `tests/README.md`.

## Что это

Фиксы и моды самой сборки S.T.A.L.K.E.R. G.A.M.M.A., **не связанные с кооперативом xrRazom** (работают и в соло).
Репозиторий — источник раздачи секции MO2 «GAMMA Sync»: `host/publish.bat` публикует секцию в `mods/` + `pack/pack.json`,
GitHub Actions прогоняет тесты и выпускает релиз, агент у остальных ставит его (подробно — `specs/system/overview.md`).

Фиксы для кооператива xrRazom — в соседнем репозитории
[xrRazom-GAMMA-fixes](https://github.com/EduardHavron/xrRazom-GAMMA-fixes) (секция «xrRazom Sync»). Архитектура у них
одна; отличаются имена: секция, маркер (`gfix_pack.txt` / `xrrfix_pack.txt`), папка агента (`%LOCALAPPDATA%\gfix` /
`\xrrfix`), задача Планировщика, архив релиза (`GAMMA_fixes.zip` / `xrRazom_fixes.zip`), переменные окружения
(`GFIX_*` / `XRRFIX_*`). Куда класть мод:
- **сюда** — фикс или мод самой GAMMA (её модов), который нужен и в соло. Если для того же мода делалась и кооп-часть
  (смежная проблема в xrRazom, например «Передать несколько» в QCT или аватар пира в Loot Claim), она остаётся в этом же
  моде — мод не делится между репозиториями;
- **в xrRazom-GAMMA-fixes** — фикс проблемы, которая появилась именно из-за xrRazom (синхронизация хост/пир, пир-зеркала,
  Taskboard Redesign у пира и т.п.).
Правку инфраструктуры (`host/`, `installer/`, `agent/`, `.github/`, `tools/`) по возможности переносить в оба репозитория.

Пушат двое (владелец и KDVFirehawk), часто параллельно. **Перед работой — `git pull`**, перед пушем — ещё раз.

## Главные правила

1. **SDD: спека → код → тесты → документация.** Любое изменение поведения начинается с `specs/`. Код, который делает не то,
   что написано в спеке, — баг кода или спеки; разница не остаётся молча.
   **Модель — «живая спека»:** один документ на компонент, правится на месте; новую спеку «под изменение» не заводим,
   история — в git и в разделе «История версий». Подробно — `specs/README.md`.
2. **`mods/` и `pack/pack.json` пишет только `host/publish.ps1`.** Моды правятся в MO2 (`<GAMMA>\mods\<мод>`), затем
   `host\publish.bat`. Руками в `mods/` не коммитить: publish считает такую правку чужой и устроит конфликт.
3. **Байт-в-байт.** `.gitattributes` = `* -text`; в коопе xrRazom сверяет файлы модов хоста и пира и не пустит в игру при
   любом расхождении. Не нормализовать переводы строк, не пересохранять файлы модов редактором с другой кодировкой.
4. **Каждый фикс — отдельный мод.** Один мод — в одном пакете: перенос между этим репозиторием и xrRazom-GAMMA-fixes —
   сначала publish пакета, откуда мод уходит, потом пакета, куда приходит (иначе установщики перетягивают его друг у друга).
5. **Кодировки служебных файлов** (REPO-015): `.ps1`, `.txt` с кириллицей и `publish.ini` — UTF-8 с BOM; `.bat` — ASCII + CRLF.
   Скрипты должны работать в Windows PowerShell 5.1 (никаких `??`, `?.`, `&&`, `-AsHashtable`).
6. **Не зашивать имена папок с версией.** Имя стороннего мода с версией (`Combined GAMMA NPC Loot Claim v.…`) тесты
   берут из `pack/pack.json`: папку может переименовать любой из публикующих. В документации имя пишется так же, как
   в `pack/pack.json` **на момент коммита** — после чужой публикации сначала `git pull` и сверка.
7. **Язык.** Документация (`README.md`, `specs/`, этот файл) — по-русски. Код, комментарии в скриптах, имена тестов,
   `COVERAGE.md`, сообщения коммитов — по-английски.

## Как устроен фикс

- Мод: `zz <Название> Fix`, внутри `gamedata/scripts/zz_xrrfix_<имя>.script` (префикс скриптов и лога `[XRRFIX]` — общий
  с xrRazom-GAMMA-fixes: моды переезжают между пакетами без правки файлов). Префикс `zz` — чтобы грузиться после патчимых
  модов.
- Значения из `.ltx` меняются только через DLTX: `gamedata/configs/mod_system_<имя>.ltx` с `![секция]` и только нужными
  ключами. DLTX применяет такие файлы по алфавиту, последний выигрывает — имя файла должно сортироваться после того, что
  переопределяем (пример — FX-LEDGE в xrRazom-GAMMA-fixes). Целые `.ltx`/`.script` чужих модов не копировать.
- В начале скрипта блок-комментарий: какой мод чинит, на чьей машине ставить, симптом, причина, решение.
- Лог через `printf("[XRRFIX] <область>: ...")`; одна строка при установке патча (это «лог-маркер» в спеке), диагностика —
  с ограничением количества. `printf`/`strformat` Anomaly подставляют только `%s`: числа форматировать заранее
  (`printf("%s", string.format("... %d ms", n))`).
- Патч ставится в `on_game_start`, под `pcall`, один раз (флаг вида `__xrrfix_wrapped`), и **безвреден**: без зависимых
  модов ничего не меняет. Фикс работает в соло; xrRazom не обязателен. Если мод что-то делает в коопе (например QCT),
  `Xrr*` API вызываются только при наличии (`XrrIsHost and XrrIsHost()`), а поведение в коопе описывается в спеке.
- Знать про кооп (если играют в xrRazom): хост авторитетен, задания генерирует хост, пир зеркалит мир и не сохраняется.
  Логи игры: `<Anomaly>\appdata\logs\xray_*.log`.

## Как чиним баг: разбор → фикс → проверка

Три шага, каждый со своим результатом; следующий не начинается, пока не готов предыдущий.
1. **Разбор.** Симптом глазами игрока, воспроизведение, логи (`xray_*.log` хоста и пира). Причина — со ссылкой на код
   (файл, функция) или строку лога. Что вывели косвенно — помечаем `[НЕ ПРОВЕРЕНО]`. Результат — разделы «Проблема» и
   «Причина» спеки. Код на этом шаге не пишем; если причина в C++ движка и Lua её не исправит — так и записать.
2. **Фикс.** Только то, что следует из разобранной причины. Если по ходу нашлось что-то за пределами разбора — дописать
   в «Причину» или в «Ограничения», а не чинить молча.
3. **Проверка.** Автотесты по требованиям, затем в игре — исходный сценарий из «Проблемы». Итог — поле
   `Проверка в игре:` в шапке спеки (`подтверждено` / `частично` / `не подтверждено` / `не проводилась` / `не записана`,
   правила — `specs/README.md`) и колонка «В игре» в README. Зелёные тесты без проверки в игре — это `не проводилась`,
   а не `подтверждено`. Изменили код фикса — вердикт снова `не проводилась`.

## Чек-листы

### Новый фикс
1. `specs/fixes/fx-<код>.md` по шаблону из `specs/README.md`: шапка (статус, проверка в игре, мод, скрипт и конфиг, где
   ставить, зависит от, лог-маркер), Проблема / Причина (файлы и функции затронутых модов, строки логов) / Решение /
   Требования `FX-<КОД>-NNN` с *Дано/Когда/Тогда* и `[auto]`/`[manual]` / Безопасность / Ограничения / Проверка в игре.
   Статус `черновик`, `Проверка в игре: не проводилась`.
2. Мод в `<GAMMA>\mods`, включить в секции «GAMMA Sync».
3. `tests/lua/test_<код>.lua` (подключить в `tests/lua/run.lua`): каждое требование `[auto]` — хотя бы один тест,
   имя теста начинается с ID требования.
4. `tests/lua/COVERAGE.md` — строка на каждое требование (`[manual]` тоже, с пометкой `manual`).
5. Реестр фиксов в `specs/README.md` и таблица «Состав пакета» в `README.md` (формат ниже, «В игре» = значение из шапки).
6. `tests/README.md`, если поменялось описание набора (например число фиксов в строке `tests/lua`).
7. Тесты локально. Пока мода нет в `mods/` репозитория, Lua-тесты запускаются на дереве с ним:
   `GFIX_TEST_ROOT=<папка с pack/ и mods/>`.
8. `host\publish.bat` — публикует мод и следом, отдельным коммитом, спеку, тесты и документацию из клона (PUB-045), если
   `tools/spec_check.py` не нашёл ошибок (PUB-046). При ошибках мод всё равно уходит, а документация остаётся в клоне —
   исправить и запустить `publish.bat` ещё раз.
9. После проверки в игре — обновить `Проверка в игре:` в шапке и «В игре» в README, запись о проверке в спеке.

### Изменение существующего фикса
1. Сначала спека: поправить требования (номера не переиспользуются, удалённые — `~~зачёркнуто~~ (удалено)`), Причину/Решение.
2. Код мода в MO2, тесты и `COVERAGE.md` под новые требования.
3. `README.md`, если поменялось «Что делает» или «Где нужен». `Проверка в игре:` → `не проводилась` (шапка и README).
4. Тесты → `publish.bat` (мод и документация двумя коммитами).

### Сторонний или переработанный мод в секции
1. Строка в таблице «Состав пакета» `README.md` и в разделе «Другие моды» `specs/README.md`.
2. Спека `specs/fixes/mod-<код>.md` (`MOD-<КОД>-NNN`) — по желанию, но если есть тесты, то спека обязательна.
   Описание от автора мода (SDD, README, план проверки) переносится в эту спеку по шаблону: устройство — в «Решение»,
   ограничения — в «Вне области», план — в «Проверка в игре», история версий — в «История версий». В папке мода
   документацию не держать: она уходит игрокам вместе с модом и теряется, если папку опубликуют под другим именем.
3. Тесты на настоящем скрипте мода, имя папки — из `pack/pack.json`.

### Переименование или удаление мода
- `README.md`, реестр `specs/README.md`, шапка спеки и ссылки на файлы внутри папки мода (они ломаются при переименовании).
  Публикация с другим именем папки — это удаление старого мода и добавление нового: файлы, которых нет в вашей копии
  (например чужой `SDD.md`), из репозитория пропадут. Удалённый фикс: спеке статус `удалено`, тесты убрать из `run.lua`,
  строки в `COVERAGE.md` — с пометкой.

### `host/`, `installer/`, `agent/`, `.github/`
1. Спека в `specs/system/` (`PUB`, `INS`, `AGT`, `CI`, `REPO`, `SYS`).
2. Код, тесты в соответствующем наборе (`tests/publish`, `tests/agent`, `tests/python`) и его `COVERAGE.md`.
3. `README.md` (разделы «Публикация», «Агент»), `agent/README.txt`, `installer/README.txt` — если меняется то, что видит игрок.
4. Изменения `installer/`, `agent/`, `release.yml`, `.github/scripts/` **выпускают релиз**, а агент самообновляется у всех —
   пушить только с зелёными тестами.

### Сверка спек, тестов и документации
- `python tools/spec_check.py` — механическая сверка (только чтение, `specs/system/spec-check.md`): у каждого `[auto]`
  требования есть тест; тесты не ссылаются на несуществующие ID; `COVERAGE.md` полный; README и реестр совпадают с
  `pack.json`; у каждого мода есть `Проверка в игре:` и README с ней согласован; сколько `[НЕ ПРОВЕРЕНО]` в спеках.
  Запускать перед каждым коммитом спек, тестов и документации. Ошибки валят `tests/python` (CHK-008), предупреждения —
  только `::warning` в Actions.
- В `COVERAGE.md` требование, которое проверяют тесты другого ID, пишется `via <ID>` (например `REPO-001 … via PUB-010`);
  известный пробел — `GAP: <что не проверено>`.
- `/spec-check` — навык Claude (`.claude/skills/spec-check/`): тот же отчёт плюс смысловая сверка изменённых спек с кодом
  модов и тестами. Только отчёт, правки — после согласия.
- REPO-017 (сверка README с `pack.json`) не блокирует релиз: публикация из MO2 не должна зависеть от README.

### Только документация
`publish.bat` публикует и её одну, без модов. `specs/`, `tests/`, `tools/`, `README.md`, `CLAUDE.md` релиз не запускают
(REPO-016), только тесты.

## Формат таблицы «Состав пакета» в README.md

Одна таблица на все моды пакета, порядок — фиксы, потом сторонние моды:

```
| Мод | Что делает | Где нужен | В игре | Спека |
| <имя папки как в pack.json> | <результат глазами игрока, без «чинит»> | у каждого / хост / кто крафтит | <Проверка в игре из шапки> | [FX-<КОД>](specs/fixes/fx-<код>.md) |
```

«Где нужен» берётся из шапки спеки («Где ставить»), «В игре» — из поля `Проверка в игре:`. Особые условия мода (заглушки, конфликтующие моды) — коротким пунктом
под таблицей, а не в ячейке.

## Тесты

| Набор | Что | Команда (из корня) |
|---|---|---|
| `tests/python` | `build_pack.py`, workflow, статика репозитория | `python -m unittest discover -s tests/python -v` |
| `tests/lua` | фиксы и моды на заглушках игровых API | `python tests/lua/run_local.py` (`pip install lupa`) или `luajit tests/lua/run.lua` |
| `tests/publish` | publish + installer | `powershell -NoProfile -ExecutionPolicy Bypass -File tests\publish\run.ps1` |
| `tests/agent` | агент | `powershell -NoProfile -ExecutionPolicy Bypass -File tests\agent\run.ps1` |

- Имя теста начинается с ID требования: `H.case("FX-TGEN-004 ...")`, `Test-Case 'PUB-012 ...'`.
- Lua-тесты грузят **настоящий** скрипт из `mods/` (`H.load_fix`); сторонние модули — маленькие заглушки с теми же
  сигнатурами. Новый колбэк X-Ray — добавить в `KNOWN_CALLBACKS` в `tests/lua/harness.lua`.
- Спека говорит одно, а код другое и чинить пока не будем — `H.xfail(...)` (EXPECTED-FAIL), отметить в `COVERAGE.md`
  и `tests/README.md`. Сейчас таких нет.
- Новый набор тестов проверять мутациями: сломать копию скрипта (`GFIX_TEST_ROOT`) и убедиться, что падает нужный тест.
- PowerShell-наборы работают во временных папках и не трогают реальные моды, `%LOCALAPPDATA%\gfix`, планировщик и GitHub.
  `tests/publish` и `tests/agent` не запускать одновременно.
- CI: `.github/workflows/tests.yml` (ubuntu: python + lua; windows: PowerShell 5.1) на каждый push; `release.yml` без
  зелёных тестов релиз не создаёт. После пуша — проверить прогон: `gh run list --limit 3`.

## Git

- `publish.bat` делает до двух коммитов: моды (`mods/`, `pack/`) и документацию (`specs/`, `tests/`, `tools/`,
  `.claude/skills/`, `README.md`, `CLAUDE.md`). Код, который уходит всем через агента и релиз (`host/`, `installer/`,
  `agent/`, `.github/`), коммитим вручную и только с зелёными тестами.
- Сообщения коммитов — по-английски, в повелительном или описательном виде, по одной теме на коммит.
- Если CI упал после чужого параллельного пуша — сначала `git pull`, смотреть, что изменил соавтор, а не откатывать его правку.
